# B0 — The `count` trap

What does `terraform plan` show when a middle landlord account is removed from the list? Why is
that dangerous here? What's the fix?

## What the plan shows

Reproduced against the seeded state (`terraform plan -refresh=false`, full output in
`logs/04_b0_count_remove.txt`) after removing `la-002` from `["la-001","la-002","la-003","la-004"]`:

```
# aws_s3_bucket.landlord_media[1] must be replaced
    ~ bucket = "haven-media-la-002" -> "haven-media-la-003" # forces replacement
# aws_s3_bucket.landlord_media[2] must be replaced
    ~ bucket = "haven-media-la-003" -> "haven-media-la-004" # forces replacement
# aws_s3_bucket.landlord_media[3] will be destroyed
    - bucket = "haven-media-la-004" -> null
Plan: 4 to add, 0 to change, 3 to destroy.   (2 of the adds are the unrelated B1 listing_media resources)
```

Terraform tracks `count` instances by **list position**, not by which landlord they belong to.
Removing index 1 shifts everyone after it down by one. `[1]` now has to become la-003's bucket,
and `[2]` has to become la-004's. Because the bucket name is immutable, both are planned as
destroy and recreate, and `[3]` is destroyed outright. One intended deletion becomes **three
destroys and two recreates**.

## Why that's dangerous here

- **Collateral data loss.** These are per-landlord media buckets. Offboarding la-002 would
  destroy la-003's and la-004's buckets, which are two *paying, unrelated* customers. In the
  default ordering Terraform plans the destroy first, so the data is gone before the replacement
  exists. If a non-empty bucket blocks the destroy, the apply fails partway through. If
  `force_destroy` is ever turned on, the objects are deleted with it.
- **Name collisions and downtime.** The "new" `[1]` wants the name `haven-media-la-003`, which is
  still held by the old `[2]` until that one is destroyed. S3 names are global and can take time
  to free up, so the apply can fail halfway, leaving buckets missing.
- **The plan is easy to misread.** A reviewer expecting "remove la-002" sees `landlord_media[1]`,
  `[2]` and `[3]` change. The index addresses hide *which landlord* each line affects.
- **It hides on a normal plan.** As `main.tf` notes, a refreshing plan with dummy credentials
  quietly drops resources from state and shows plain creates instead, so the cascade isn't
  visible unless you diff against state.
- **Billing is wrong.** Recreated buckets get fresh resource IDs and lose their history
  (lifecycle state, replication, policies attached outside this module). Per-landlord cost
  attribution breaks for accounts that didn't change.

## The fix

Key the resource by a **stable identity**, the landlord account ID, using `for_each`, and migrate
existing state with `moved` blocks so the refactor itself doesn't recreate anything
(see `terraform/main.tf`):

```hcl
resource "aws_s3_bucket" "landlord_media" {
  for_each = toset(var.landlord_accounts)
  bucket   = "haven-media-${each.key}"
  tags     = { landlord_account_id = each.key }
}

moved {
  from = aws_s3_bucket.landlord_media[0]
  to   = aws_s3_bucket.landlord_media["la-001"]
}
# ... [1] -> "la-002", [2] -> "la-003", [3] -> "la-004"
```

Verified results:

| Scenario | Result | Log |
|---|---|---|
| Fix applied, all 4 accounts present | 4 × `has moved`, **0 to destroy** (pure state migration) | `logs/06_b0_foreach_migrate.txt` |
| Fix applied, `la-002` removed | 3 × `has moved`, **1 to destroy: `landlord_media["la-002"]` only** | `logs/05_b0_foreach_remove.txt` |

Rollout notes:
- Ship the `for_each` change and `moved` blocks **as their own change, with no account removed**,
  and confirm the plan shows 0 to destroy. Remove `la-002` in a later, separate PR. Keep the
  `moved` blocks until every workspace or environment has applied them. They're harmless to leave.
- The index-to-ID mapping in the `moved` blocks must match the order in the *actual state*.
  Verify it with `terraform state list` and `terraform state show` per environment rather than
  trusting the variable's current order.
- If the order isn't known for some environment, use `terraform state mv` there as a one-off.
- Guardrails worth adding: `lifecycle { prevent_destroy = true }` on customer-data buckets (an
  intentional offboarding removes it in the same reviewed PR), and a CI policy check that fails
  any plan containing `delete` on `aws_s3_bucket` unless it's explicitly approved.
- Going further, `var.landlord_accounts` could become a `set(string)` or a `map(object)` keyed by
  ID. A `map(object)` also leaves room for per-account settings without going back to positional
  lists.
